## [2026-07-28] Shopify orders are NOT searchable by phone
**Mistake/Issue:** `orders(query:"phone:...")` silently ignores the phone filter — it looks like it works but returns unfiltered results.
**Correct:** maintain our own `order_mappings` (phone_e164 → order_gid) filled from the `orders/create` webhook; fallback: `customers(query:"phone:...")` → `orders(query:"customer_id:...")`.
**Pattern:** verify every Shopify query filter against shopify.dev's supported-filter list before designing around it.

## [2026-07-28] Two different webhook HMAC schemes in one app
**Mistake/Issue:** Meta and Shopify both send HMAC-SHA256 signatures but encode them differently — copying the cafe verifier for Shopify would silently reject every webhook.
**Correct:** Meta `X-Hub-Signature-256` = **hex**; Shopify `X-Shopify-Hmac-Sha256` = **base64**. Two verifiers, both on the RAW body, constant-time compare.
**Pattern:** never reuse a signature verifier across providers without checking the encoding.

## [2026-07-28] Template quick-reply taps are message type "button", NOT interactive.button_reply
**Mistake/Issue:** A tap on a TEMPLATE quick-reply button arrives as `type:"button"` with `button.{text,payload}` + `context.id`; the cafe inbound parser only handles `type:"interactive"` (`interactive.button_reply`) and returns `None` for unknown types — so copying it wholesale makes every Confirm/Cancel tap fail SILENTLY (found by architecture review F4, before any code was written).
**Correct:** add an `InboundButton` variant to the typed union; template sends must attach an explicit per-button `payload` (≤128 chars, e.g. `order:confirm:{gid}`) or Meta returns only the language-dependent button text.
**Pattern:** when copying a channel parser across a message CLASS (template vs interactive), re-verify the inbound webhook shape against the provider's reference — not just the outbound payload.

## [2026-07-28] Vercel Python has no reliable "process after response" — use a durable outbox
**Mistake/Issue:** The plan said "ack Shopify 2xx <5s, process after" — but FastAPI BackgroundTasks on Vercel's buffered Python runtime run INSIDE the request cycle (delaying the response), and post-response work can be killed on instance reclaim. Combined with webhook-id idempotency, a lost send is never retried: customer silently gets no message (review F1).
**Correct:** webhook handler = one short DB transaction (dedupe insert + mapping upsert + `outbound_messages` queue row) → 200. A separate cron/self-invoked drain sends from the outbox with retries; `dedupe_key` UNIQUE makes "one push per order ever" a DB invariant.
**Pattern:** on serverless, anything that must survive the request needs a durable queue/table — never in-process background work.

## [2026-07-28] hmac.compare_digest raises TypeError on non-ASCII str — compare bytes for header values
**Mistake/Issue:** `hmac.compare_digest(a, b)` with two `str` raises `TypeError` if either contains a non-ASCII char. Starlette decodes HTTP headers latin-1, so an attacker header byte `\xe9` reaches the verifier as a non-ASCII str → 500 on the Shopify HMAC check and the cron `X-Cron-Secret` check.
**Correct:** encode both sides to bytes before comparing — `candidate.encode("ascii")` inside `try/except UnicodeEncodeError: return False` (fail closed), then `compare_digest(expected.encode("ascii"), provided)`.
**Pattern:** any secret/signature compare on a value that originated in an HTTP header must be a bytes compare guarded against non-ASCII input — never `compare_digest` on two raw strs.

## [2026-07-28] Webhook payload fields must be type-coerced — a 500 on a signed delivery deletes the subscription
**Mistake/Issue:** JSON fields were read with the wrong shape assumed (`payload.get("phone")` an int → `normalize_phone` TypeError; `customer` a str → `.get` AttributeError; `payment_gateway_names` an int → not iterable; unvalidated `email`/`financial_status` into asyncpg text params → DataError). Each is a 500 on a signature-valid delivery, and Shopify deletes a webhook subscription after 19 consecutive failures — so one poison-but-signed payload can silently unhook order ingestion.

**Pattern:** on a signed webhook, treat every payload field as attacker-typed — a 500 is not a transient error, it burns the provider's retry budget and can tear down the integration.

## [2026-07-28] A None-returning "is it ours?" extractor makes the tenant guard fail OPEN
**Mistake/Issue:** WhatsApp `_incoming_phone_number_id` returned `None` for BOTH "metadata absent" and "phone_number_id not a str", and the caller only enforced the tenant check `if value is not None`. So a payload omitting `metadata`, or sending a non-str id, skipped the check and was processed as ours (signed-envelope PoC returned 200 as a real event). Same envelope-parsing also read only `messages[0]`/`entry[0]`/`changes[0]` — Meta batches multiple messages per delivery, so everything after the first was silently dropped while the whole batch was 200-acked (Meta never retries an acked delivery = permanent loss of e.g. a "cancel my order").
**Correct:** fold the tenant check INTO extraction and fail CLOSED — `extract_events(payload, expected_phone_number_id)` processes a change only if `metadata.phone_number_id` is present, a `str`, and `==` ours; iterate ALL entries/changes/messages, dedupe each via `record_if_new`, return aggregate `{processed, duplicate, results:[...]}`. Enforcement must not branch on "malformed vs mismatched" — both reject.
**Pattern:** a guard whose sentinel (`None`) collapses "absent" and "wrong-type" into the same value as "checked-and-ok-to-skip" fails open. Decide present-str-and-equal in one predicate; and any per-index (`[0]`) webhook parse silently drops a provider's batch — iterate all and ack an aggregate.

## [2026-07-30] A router-level Depends cannot cap request-body size — FastAPI parses the body first
**Mistake/Issue:** The Phase-3.5 plan enforced the admin 1 MiB body cap with a router dependency `enforce_body_cap(request)` on `admin_router`. It does not work: FastAPI reads and JSON-parses the request body (for the pydantic body param) BEFORE it runs path/router `Depends`, so an oversized *invalid-JSON* body returns **422 `json_invalid`** before the cap check ever runs. The plan's `test_body_cap_413` asserts 413 → failed.
**Correct:** enforce the cap at the ASGI layer, before routing/body-parse — a tiny pure-ASGI middleware (`AdminBodyCapMiddleware`) that 413s `/admin` requests whose `Content-Length` exceeds the cap. This is exactly how the existing webhook edges do it (`app/channels/{whatsapp,shopify_webhook}.py` read the raw body and check `content-length` + `len(raw)` themselves, taking `request: Request` instead of a parsed body param). Register with `app.add_middleware(...)` at import time (before first request, else Starlette raises "Cannot add middleware after start").
**Pattern:** any cross-cutting check that must beat body parsing (size caps, raw-HMAC on the exact bytes) belongs in middleware or a raw-body handler — NOT a FastAPI dependency on a body-param route. Dependencies run after the body is already parsed.

## [2026-07-30] FastAPI's DEFAULT 422 handler echoes `input` — over-length creds leak; and `RequestValidationError.errors()` takes NO kwargs
**Mistake/Issue:** Two distinct traps found in the Phase-3.5 security review. (1) FastAPI ships NO custom `RequestValidationError` handler by default — its built-in serializes each pydantic error dict WITH `input`, so POSTing an over-length `api_key`/`client_secret`/`access_token`/`password` (any `Field(max_length=…)`-capped secret) returns a 422 whose body echoes the submitted secret verbatim (→ browser devtools/HAR, proxies, error monitors = plaintext-secret leak, CLAUDE.md Rule 1). (2) The obvious fix — `exc.errors(include_url=False, include_input=False, include_context=False)` — RAISES `TypeError: ValidationException.errors() got an unexpected keyword argument 'include_url'`, because FastAPI's `RequestValidationError.errors()` is NOT pydantic's `ValidationError.errors()`; it returns the pre-computed list and accepts no kwargs. (Those kwargs DO work on a raw pydantic `ValidationError`, e.g. the `put_knowledge` path that catches `validate_and_serialize`'s error — different class, different method.)
**Correct:** register a global `@app.exception_handler(RequestValidationError)` that filters the dicts by hand — `[{k: v for k, v in err.items() if k not in ("input", "url", "ctx")} for err in exc.errors()]` → `JSONResponse(422, {"detail": …})`. Drop `ctx` too (a custom validator's raw `ValueError` object there is non-JSON-serializable → 500 on render) and `url` (noise doc link). For code paths that catch a raw pydantic `ValidationError` directly, the `errors(include_url=False, include_input=False, include_context=False)` kwargs are correct and available.
**Pattern:** on any FastAPI app, add a `RequestValidationError` handler that strips `input` before deploying a route with a secret-bearing body field — the default handler is a credential-echo vector. And never assume `RequestValidationError.errors()` == pydantic `ValidationError.errors()`: the FastAPI wrapper takes no kwargs; strip keys manually.

## [2026-08-04] Vercel Python runtime: asyncpg dual-stack getaddrinfo → OSError [Errno 16] EBUSY
**Mistake/Issue:** In production on Vercel the app could not open a DB connection to the Supabase transaction pooler (`aws-1-ap-south-1.pooler.supabase.com:6543`) even with a correct host and correctly percent-encoded password. The traceback died at `pg_factory.py acquire -> asyncpg pool -> connect_utils._create_ssl_connection -> loop.create_connection -> _ensure_resolved -> loop.getaddrinfo -> socket.getaddrinfo -> OSError: [Errno 16] Device or resource busy`. Root cause: asyncpg resolves the host through asyncio's threaded executor with `AF_UNSPEC` (dual-stack IPv4+IPv6); that threaded getaddrinfo path is broken on the Vercel Python runtime and fails with EBUSY — the DSN/password are fine, it never gets past DNS resolution.
**Correct:** in `LazyPool._get_pool`, ONLY when the DSN hostname contains `supabase.com`, resolve IPv4 synchronously in-process (`socket.getaddrinfo(host, None, family=socket.AF_INET, type=socket.SOCK_STREAM)[0][4][0]`) and call `asyncpg.create_pool(dsn, host=<ipv4>, ssl="require", min_size=0, max_size=5, statement_cache_size=0)`. The explicit `host=` kwarg overrides the DSN host (asyncpg precedence: kwarg wins), avoiding asyncio's broken dual-stack resolver; `ssl="require"` encrypts without hostname verification (mandatory because connecting by IP defeats hostname verification). Wrap the resolution in `try/except OSError` → fall back to the plain `create_pool(dsn, ...)` so it never hard-fails worse than today. Non-supabase DSNs keep the EXACT current behavior (no host override, no `ssl` kwarg) — local/test DBs may be plain non-SSL Postgres. Only `app/store/pg_factory.py` changed.
**Pattern:** on Vercel's Python serverless runtime, asyncio's threaded AF_UNSPEC getaddrinfo can EBUSY — force `AF_INET`, resolve synchronously, connect by the resolved IP, and add `ssl="require"` to restore encryption lost by connecting to an IP. Scope such a runtime-specific workaround to the exact host family (`supabase.com`) so other DBs are untouched. This class of bug only reproduces on the runtime — tests can validate the connect-kwargs wiring (mock `socket.getaddrinfo` + `asyncpg.create_pool`) but not the fix itself.

## [2026-08-06] `str.isdigit()` is not a safe int-parsing gate — Unicode digits pass isdigit() but disagree with int()
**Mistake/Issue:** `controls.load_controls` gated the `_INT_KEYS` parse with `if raw.isdigit(): data[key] = int(raw)`. `str.isdigit()` is Unicode-aware and does NOT agree with `int()` in either direction: `"²".isdigit()` is `True` but `int("²")` raises `ValueError` (→ uncaught 500 that bricks GET /admin/controls), while other Unicode-decimal forms (`"٣٠"`) pass isdigit() and int() alike but were never a real operator input. A corrupted/attacker-written stored value could thus either crash the endpoint or silently enable an unintended retention period. The same class of bug lived unguarded on the SIGNED Shopify webhook hot path: `float(staleness_raw)` in `channels/shopify_webhook.py` — a non-numeric stored `push_staleness_hours` → `ValueError` → 500 on a signature-valid delivery, burning Shopify's 19-failure retry budget before it deletes the subscription (the higher-blast-radius version).
**Correct:** never use `str.isdigit()`/`str.isdecimal()` as a pre-check for `int()`/`float()`. ⚠ **Round-1 note (superseded — see 2026-08-06 "ASCII-digit gate" entry below):** the first fix used `try: value = int(raw) except ValueError: pass` / `try: return float(raw) except ValueError: return DEFAULT`. That closes the *crash*, but `int()`/`float()` are themselves Unicode-permissive (`int("٣٠") == 30`, `float("٣٠") == 30.0`), and `float()` also accepts `nan`/`inf`/`1e400` without raising — so the Unicode-bypass and a fail-open non-finite value were still open. The COMPLETE gate is `raw.isascii() and raw.isdigit()` **then** parse (+ `math.isfinite` + range clamp on the float path). Same "treat every stored/typed value as attacker-typed, degrade to a safe default, never crash" posture as the 2026-07-28 "Webhook payload fields must be type-coerced" entry.
**Pattern:** `isdigit()`-then-`int()` is a latent 500 (and a silent-misconfig) vector — the two functions do not share a definition of "a number." Neither does `int()`/`float()` alone close it (Unicode-permissive; `float` also fail-opens on nan/inf). Require `str.isascii() and str.isdigit()` before parsing, then bound the result. Reserve `isdigit()` for genuinely display-only checks. (Related: `re`/pydantic `\d` is Unicode-aware too — pin phone/E.164 patterns to `[0-9]`, not `\d`; and Python `re`'s `$` matches before a trailing `\n`, so anchor with `\Z`.)

## [2026-08-06] Round-2 fix: `int()`/`float()` alone don't close the Unicode-digit bypass; `float` fail-opens on nan/inf; and `$` matches before a trailing newline
**Mistake/Issue:** The round-1 fixes above were re-verified and found INCOMPLETE (a two-round fix, not a one-shot close).
