## Admin template resend send path (Task 2 of 3, 2026-08-19)
- **File:** app/admin/router.py (`list_templates`, `send_admin_template`, `TemplateSendRequest`);
  app/jobs/outbox_drain.py (`_ADMIN_RESEND_DEDUPE_PREFIXES`).
- **Purpose:** admin-triggered resend of one of the store's 4 approved templates for a specific
  order, with admin-editable field values, for the chat page's emoji/template picker.
- **Public API:** `TemplateSendRequest{order_name: str, template: str, values: dict[str,str]=\{\}}`
  (`order_name`/`template` ≤64 chars, each `values` entry ≤1024 chars — length bounds added in the
  final fix wave); `list_templates(thread_id) -> {"orders": [{"order_name", "templates": [{"key",
  "label", "has_buttons", "fields": [{"key","label","value","read_only"}]}]}]}` (read-only; each
  order's `templates` list is now FILTERED via `_template_applies_to_order` — a cancelled order
  drops `cod_confirmation`/`prepaid_order`, an unfulfilled order drops `order_shipped`/
  `order_delivered` — fix-wave addition); `send_admin_template(request, thread_id, body, response)
  -> {"ok": True, "status": "sent"|"suppressed"|"queued"} | {"ok": False, "error": str}` (widened
  in the fix wave from a bare `{"ok": bool}` to distinguish the three non-failure outcomes — `None`
  outcome from `send_inline_outbound` means the row is queued for the backstop drain, not sent).
- **Used in:** admin chat page (`chats.js`'s template dialog, Task 3 — see below).
- **Notes:** goes through the SAME `enqueue_outbound` + `send_inline_outbound` pipeline as every
  automatic template send (order confirmation/shipped/delivered) — respects `send_mode`/
  `allowlist_phones` exactly like those, deliberately UNLIKE the sibling `send_manual_reply` (free
  text), which bypasses the kill switch by design. `cod_confirmation`'s Confirm/Cancel button
  payloads are built from `order.gid` resolved server-side via `find_mirrored_orders_by_phone` —
  never from the request body; the `order_id`/`order_name` display field is now force-pinned
  server-side too (fix-wave addition — an admin-editable text field could previously desync from
  the gid the buttons actually act on; read-only in the UI). `dedupe_key =
  f"admin_resend:{order.gid}:{template}:{uuid4()}"` — the `admin_resend:` prefix must stay
  registered in `outbox_drain.py`'s `_DEDUPE_PREFIXES` (same family as
  `_FULFILLMENT_DEDUPE_PREFIXES`, no `order_mappings.status` side effect) or every resend silently
  fails `bad_dedupe_key`. **Fix-wave addition:** every resolved field value that is blank
  (admin-cleared + no default) is substituted with the existing `EMPTY_PARAM_PLACEHOLDER`
  convention (`app.channels.copy`) before the send, matching every other template send call site —
  Meta rejects a literal empty string body param.

- **Purpose:** dedicated standalone admin page for reading a customer's merged WhatsApp thread (AI replies, template sends, button taps) alongside their Shopify order history — replaces the embedded "Chats" card previously in `index.html`/`admin.js` (removed 2026-08-17, see below).
- **Public API:** static page, no exports. Reachable at `/admin/ui/chats.html` (same `StaticFiles(directory=app/admin/static, html=True)` mount at `/admin/ui`, no new route registration). Three-pane layout: thread list (with a client-side search box) | chat bubbles (with per-message delivery-status labels) | order-details panel (order number + product list + dropdown selector when a customer has multiple mirrored orders). Consumes `GET /admin/conversations` (thread list) + `GET /admin/conversations/{thread_id}` (merged timeline + `orders` array — see api_registry.md's BREAKING response-shape note + the 2026-08-17 chat-page-polish field additions below it).
- **Used in:** admin operators only (direct URL, no link from the settings panel — deliberate, per owner choice).
- **Notes:** same `require_admin` session-cookie auth as every other admin route, no new auth mechanism. Strictly READ-ONLY — no send capability (send UI is deferred to sub-project 2 of the "admin WhatsApp chat tool" effort, manual send + 24h-window timer, unbuilt/unbrainstormed). Deliberately uses WhatsApp's own green palette (`#00a884` headers, `#efeae2` background, `#d9fdd3` outgoing bubbles) instead of the app's indigo admin palette — explicit owner choice, not an inconsistency. XSS posture: `.textContent`/`createTextNode` throughout; the one `.innerHTML` use only ever inserts a hardcoded label. `renderOrderDetail`'s tracking link is only created when `order.tracking_url` matches `/^https?:\/\//i` (defense-in-depth fix, 2026-08-17 — a non-`http(s)` scheme skips the link element entirely rather than rendering it). Both code-reviewer and security-reviewer reviewed the full original 4-commit range and returned APPROVE with no blockers. **Removed the same day (dedicated-chat-page commit):** the embedded `chats-card` div + `#chat-header`/`#chat-thread`/`.bubble*` CSS in `index.html`, and `renderChatEntry`/`loadChatThread`/`loadChatList` (+ the `loadChatList()` call in `loadAll()`) in `admin.js` — this page supersedes it entirely, not an addition alongside it.
- **Chat Page Polish (2026-08-17, sub-project 1b — same-day follow-up, 9 commits, all local on `main`, NOT pushed).** Design: `docs/superpowers/specs/2026-08-17-chat-page-polish-design.md`; plan: `docs/superpowers/plans/2026-08-17-chat-page-polish.md`. No longer "Manual refresh only, no live polling" — the page now polls. What changed in `chats.js` (no HTML structural rewrite, `chats.html` gained the search input + product-list container elements the below functions target):
  - **Product list + always-visible order number:** `renderOrderDetail(order)` now also renders `order.line_items` into `#order-products` (`{quantity}× {title} ({variant_title}) — {price_amount} {price_currency}`, one row per item, only when items exist); `renderOrderPanel(orders)` clears BOTH `#order-number` and `#order-products` on its empty-orders branch (previously only `#order-detail` was cleared, leaving a PREVIOUS customer's order number/products on screen when switching to a thread with no orders — fixed in the final review-fix wave, commit `d9ac185`).
  - **Delivery-status labels:** `renderBubble(entry)` appends a `.bubble-status` div (only when `entry.status` is present and not `"sent"`) using the module-level `STATUS_LABELS` map (`suppressed`→"Not delivered — skipped by send policy", `failed`→"Failed to send", `undeliverable`→"Undeliverable", `queued`→"Queued"; unmapped values fall back to the raw status string); `failed`/`undeliverable` also get a `.bubble-status-error` class. Matches real WhatsApp's convention: nothing extra shown for a clean send.
  - **Thread-list search:** new `normalizeOrderQuery(query)` (strips a leading `#`, then maps bare digits to `"tavas" + digits`, mirroring `app/shopify/models.py`'s `normalize_order_name` isdigit branch) + `threadMatchesQuery(thread, query)` (matches phone, `customer_name`, or any `order_names` entry, raw or normalized) filter the already-loaded `allThreads` client-side on the `#thread-search` input's `input` event via `renderThreadRows` — no new endpoint. `renderThreadRows` also now shows `"{customer_name} (+91...)"` when a name is known, phone-only otherwise.
  - **3-second diff-checked poll:** `pollTick()` (registered via `setInterval(pollTick, 3000)`) re-fetches `GET /admin/conversations` and, if `currentThreadId` is set, `GET /admin/conversations/{thread_id}`, but only re-renders when a cheap snapshot key actually changed — `threadListKey(threads)` (`thread_id:last_active_at` joined) and `threadEntriesKey(entries)` (`count:lastTimestamp:allStatusesJoined` — folds every entry's `status` into the key, not just count+last-timestamp, so a template send's `queued`→`sent`/`failed` transition is detected even though it changes neither the count nor the timestamp; this was a real gap in the first poll implementation, fixed in the review-fix wave). Guards: skips entirely when `document.hidden` (backgrounded tab) and has a `pollInFlight` re-entrancy guard (an in-flight tick blocks the next one) — because `GET /admin/conversations` costs ~3 DB round-trips per thread row against the same small (`max_size=5`) Postgres pool the live customer-facing WhatsApp reply path shares. `loadThread(threadId, phone, silent = false)` gained the `silent` parameter so a poll-triggered `loadThread` call (`silent=true`) never writes to `#thread-status` (reserved for real user-triggered errors) on failure.
  - **Known limitations (not fixed in this pass, worth a look next iteration):** search only covers the 50 most recent threads (`GET /admin/conversations` default `limit`) and each customer's 10 most recent orders (`find_mirrored_orders_by_phone`'s cap) — no "recent only" hint shown in the UI. Zero behavioral test coverage for this frontend (only Python `TestClient` substring-presence checks against the served JS text exist — no browser/JS test runner in this repo; structural, accepted gap). The multi-order `<select>` resets to the first order whenever the poll silently re-renders the thread (selection not preserved across a poll refresh).
- **Delivery/Read Receipts (2026-08-18, sub-project 1c) — WhatsApp-style tick marks.** New `renderDeliveryMark(entry)` in `chats.js` appends a small `.delivery-mark` span next to the bubble timestamp — eligible entries are `ai_reply` (always, no `status` field to gate on) and `template_sent` with `status === "sent"` (a queued/suppressed/failed template already shows its own `.bubble-status` label instead, so no tick is added on top). Renders `"✓"` (`.delivery-mark-sent`, grey, `entry.delivery_status` null/`"sent"`), `"✓✓"` grey (`.delivery-mark-delivered`), `"✓✓"` blue (`.delivery-mark-read`), or `"!"` (`.delivery-mark-failed`, `entry.delivery_status === "failed"`). `renderBubble(entry)` calls it and appends the mark into the existing `.bubble-ts` timestamp div. The 3-second poll's `threadEntriesKey`/diff-check was widened in the same feature to fold each entry's `delivery_status` into the snapshot key (joined via `deliveryStatuses`) — the pre-existing key only hashed `status`, a different field, so a delivery→read transition on an already-rendered bubble would never have triggered a re-render without this.
- **Admin Manual Reply (2026-08-18, sub-project 1f) — free-text send box, no more switching to WhatsApp Web.** `chats.html`/`chats.js` gained a reply bar (`#reply-input` + `#reply-send-btn` + `#reply-status`) under the bubble pane, POSTing to `POST /admin/conversations/{thread_id}/messages` (see api_registry.md for the full endpoint contract). **24h-window gating (client-side, advisory only):** `loadThread` computes `lastCustomerAt` from the loaded entries and sets module-level `replyWithinWindow = (Date.now() - lastCustomerAt) < REPLY_WINDOW_MS` (`REPLY_WINDOW_MS = 24*60*60*1000`); disables `#reply-input`/`#reply-send-btn` and swaps the placeholder to "Outside the 24-hour reply window — send a template instead" when false or when there's no customer message at all. The send handler's `finally` re-enables the button only if `replyWithinWindow` (not unconditionally) so a thread that scrolled out of the window during a send stays disabled. **Thread-switch draft clearing:** `loadThread`, on a genuine switch to a DIFFERENT thread id (not a poll-triggered silent refresh of the same thread), clears `#reply-input`'s value and `#reply-status`'s text — prevents a draft typed for customer A from surviving into customer B's thread and misfiring on Enter. **`api()` extended:** `api(path, method, body)` now accepts an optional body (POSTs a bodyless request as `{}` to dodge Vercel's edge 411-on-no-Content-Length); its error branch prefers `data.error` (a plain string, this endpoint's `{"ok": false, "error": ...}` shape on 502/503) over `data.detail` (every other admin route's `HTTPException` shape) when present. **Sender-aware bubble label:** `renderBubble` labels an `ai_reply` entry `"you"` (instead of `"ai reply"`) when `entry.sender === "admin"`, sourced from the new `sender` field on `GET /admin/conversations/{thread_id}` entries (see api_registry.md). **Fix-wave addition:** on a send failure, `set_message_delivery_status` (see `ConversationStore` entry below) marks the row `"failed"` so it renders the same red `"!"` tick as any other failed delivery instead of being indistinguishable from a successful send.

## ConversationStore.mark_read / count_unread_messages (admin chat unread marker, 2026-08-19)
- **File:** backend/app/store/base.py (Protocol, lines 393-404), backend/app/store/postgres.py
  (`PostgresConversationStore`, ~1502-1526), backend/app/store/memory.py
  (`InMemoryConversationStore`, ~918-929).
- **Purpose:** admin "unread" tracking — stamp the moment the owner opened a thread in the admin
  chat page, and count customer messages newer than that stamp, for the chat page's per-thread
  unread badge + "Unread" filter chip.
- **Public API:** `mark_read(conversation_id: int, at: datetime) -> None`; `count_unread_messages(conversation_id: int) -> int`
  (counts `messages` rows with `role="user"`/customer and `created_at` strictly after the
  conversation's `last_read_at`).
- **Used in:** `app/admin/router.py` — `list_conversations` (`GET /admin/conversations`, calls
  `count_unread_messages` per thread → `unread_count` field) and `get_conversation_thread`
  (`GET /admin/conversations/{thread_id}`, calls `mark_read` as a side effect on every open/poll —
  see api_registry.md's GET-with-write-side-effect note).
- **Notes:** Postgres `mark_read` writes `last_read_at = GREATEST($1, now())`, not the raw `$1` —
  fixes a real clock-domain bug (app-process clock vs. DB-server clock stamping
  `messages.created_at`) caught in final whole-branch review, see error_learnings.md 2026-08-19
  "two clock domains, one comparison"; in-memory `mark_read` stores `at` raw (single clock domain,
  no skew possible). `messages.created_at`/`conversations.last_read_at` are Postgres `timestamptz`
  (DB-clock-comparable); a brand-new conversation defaults `last_read_at` to its creation time
  (schema `DEFAULT now()`, in-memory falls back to `datetime.min` when `mark_read` was never
  called) so pre-existing history never floods the UI with unread badges on first ship. The
  `get_conversation_thread` call site wraps `mark_read` in `try/except Exception:
  logger.warning(...)` — a failure there can never break the entries/orders response. Requires the
  `conversations.last_read_at` schema migration — see `_pipeline_status.md` CHECKPOINT.
  **Known, accepted trade-off (final-review ruling, not a TODO):** `list_conversations` now does 2
  additional per-thread round trips (`count_unread_messages` + `get_paused_until`) on its existing
  documented N+1 loop (capped `limit<=100`, hit every 3s by `pollTick`) — reviewer flagged it as
  worth noting, orchestrator ruled ACCEPT (batching would be scope creep beyond the approved
  design), same trade-off class as the loop's pre-existing N+1.

## LazyPool (asyncpg)
- **File:** backend/app/store/pg_factory.py
- **Purpose:** asyncpg connection pool created on FIRST `acquire()`, never at import (serverless cold-start rule).
- **Public API:** `LazyPool(dsn: str)`; `async with pool.acquire() as conn:`; `async close()`. Double-checked `asyncio.Lock` guards single pool creation. `create_pool(min_size=0, max_size=5, statement_cache_size=0)`.
- **Used in:** PostgresConfigRepo, PostgresIngestStore, deps.Container.
- **Notes:** asyncpg has no py.typed marker — `[[tool.mypy.overrides]] module="asyncpg.*" ignore_missing_imports=true` in pyproject.toml. **Supabase-host IPv4 pin (Vercel getaddrinfo EBUSY workaround, 2026-08-04):** when the DSN hostname contains `supabase.com`, `_get_pool` calls `_create_supabase_pool(host)` — it synchronously resolves IPv4 (`socket.getaddrinfo(host, None, family=AF_INET, type=SOCK_STREAM)[0][4][0]`) and passes `host=<ipv4>` + `ssl="require"` to `create_pool` (asyncpg kwarg overrides the DSN host; `ssl=require` encrypts without hostname verification since we connect by IP). This dodges Vercel's Python runtime raising `OSError [Errno 16] EBUSY` inside asyncio's threaded dual-stack (AF_UNSPEC) getaddrinfo. On resolution failure (`except OSError`) it falls back to the plain `create_pool(dsn, ...)` — never hard-fails worse than before. **Non-supabase DSNs are UNCHANGED** (no host override, no `ssl` kwarg) so local/other plain non-SSL Postgres still works. `statement_cache_size=0` kept on every path (transaction pooler breaks prepared statements). Wiring is unit-tested with mocks (`tests/store/test_lazypool_ipv4.py`); the bug itself only reproduces on the Vercel runtime.

- **Used in:** `channels/whatsapp.py::receive_webhook` — one `await apply_delivery_status(c, wa_cfg, status)` per `extract_statuses(...)` result, each wrapped in `try/except Exception: logger.exception(...)` so a failure never breaks the signed webhook's 200 ack.

## Delivery-failure auto-retry (resend on a fresh 'failed' status) — 2026-08-18 (sub-project 1e)
- **File:** backend/app/core/delivery_retry.py
- **Purpose:** on a genuinely new WhatsApp `'failed'` delivery status, resend the message once (same content), capped at `MAX_RETRIES`; page the store owner when retries are exhausted or a resend can never earn a future wamid to retry off of. Nothing here mutates a Shopify order — it only SENDS (Rule 2).
- **Public API:** `MAX_RETRIES: int = 3`; `_RETRY_SEND_TIMEOUT_SECONDS: float = 3.0` (module constant — short, path-specific bound on EVERY send here, resend + owner alert, since both run inline inside the WhatsApp webhook request; mirrors `outbox_drain._INLINE_SEND_TIMEOUT_SECONDS`). `async retry_failed_outbound(c: Container, wa_cfg: WhatsAppConfig, controls: AdminControls, wamid: str) -> None` — resends a template from `outbound_messages` (via `get_outbound_retry_info`/`record_outbound_retry` + `parse_payload`); `async retry_failed_message(c, wa_cfg, controls, wamid) -> None` — the `messages`/AI-reply sibling (recipient resolved from the conversation `user_id`). Private: `async _alert_owner_retry_exhausted(c, wa_cfg, controls: AdminControls, phone: str, retry_count: int) -> None`.
- **Used in:** `app/core/apply_status.py::apply_delivery_status` (the only caller) — one of the two on a fresh `'failed'`, matched to the table that owned the wamid.
- **Notes:** every send goes through the ADR-002 kill switch — the resend via `send_decision(controls.send_mode, controls.allowlist_phones, phone)` (suppressed = burn one retry, earn no fresh wamid, page owner), and the OWNER ALERT ITSELF is gated the same way on `owner_alert_number` (mirrors `conversation.py::_alert_owner`), so flipping `send_mode` to `off` during an incident stops this path too — a suppressed alert simply does not send (debug-log, no warning). `_alert_owner_retry_exhausted` degrades silently on an unset owner number, never raises, log-only on a failed send, and reports the ACTUAL retry attempts SPENT on the row (`info.retry_count` at the cap, `info.retry_count + 1` from an early-terminal branch) — not a hardcoded `MAX_RETRIES`. A successful resend writes a non-PII `logger.info` audit line (table + old/new wamid + retry_count; never the phone or content — wamids are established elsewhere as safe to log). Every send passes `timeout=_RETRY_SEND_TIMEOUT_SECONDS`.

## Fulfillment lifecycle notifications (order_shipped / order_delivered) — 2026-08-17
- **File:** backend/app/channels/shopify_webhook.py
- **Purpose:** send `order_shipped`/`order_delivered` WhatsApp templates from the existing `fulfillments/create`/`fulfillments/update` webhook branch, which previously only mirrored tracking data (`_mirror_fulfillment`) and sent nothing. Closes the gap flagged when Q10 tracking capture shipped.
- **Public API:** `TEMPLATE_NAME_SHIPPED = "order_shipped"`, `TEMPLATE_NAME_DELIVERED = "order_delivered"`, `FULFILLMENT_TEMPLATE_LANGUAGE = "en"` (both Meta-approved in `en` ONLY, same situation as every other template this app sends), `_FULFILLMENT_INLINE_SEND_TIMEOUT_SECONDS = 2.0` (module constants). `async _notify_fulfillment_events(c: Container, order_gid: str, fulfillment: Fulfillment, raw_payload: dict) -> None` — best-effort, never raises; `async _enqueue_and_send_fulfillment_notification(c, order_gid, dedupe_key, phone, template, body_params: list[str]) -> None` — builds the `OutboundDraft`, calls `enqueue_outbound` then `send_inline_outbound(..., timeout=_FULFILLMENT_INLINE_SEND_TIMEOUT_SECONDS)`, wrapped in its OWN `try/except` so it never raises past this call; `_log_notify_failure(order_gid, exc) -> None` — PII-free failure log (gid + exception TYPE + the last traceback frame's `file:line`, never `str(exc)`, which could echo a tracking number/URL).
- **Used in:** the existing `fulfillments/create`/`fulfillments/update` branch — after `_mirror_fulfillment` (mirroring stays first and authoritative), `await _notify_fulfillment_events(c, order_gid, fulfillment, payload)` runs unconditionally on every such event.
- **Notes:** **Shipped** = the parsed `Fulfillment` now has both `tracking_company` AND (`tracking_number` OR `tracking_url`) — checked on every create/update event; the PER-FULFILLMENT dedupe key (not an in-code flag) is what prevents a duplicate send on a replay or a later event where tracking was already present. **Delivered** = the RAW webhook payload's `shipment_status == "delivered"` (Shopify's own enum, read directly from `raw_payload` — NOT added to the `Fulfillment` dataclass, since it's a one-shot trigger check, not tracking data the mirror needs; confirmed present/reliable for this store's courier via a real captured production payload, not assumed). Both checks run unconditionally and independently — either or both can be newly true in the same event (rare but possible: a courier reports the full journey in one update), and each fires its own independent enqueue+send. **Idempotency:** two new dedupe-key families via the existing `enqueue_outbound` `ON CONFLICT (dedupe_key) DO NOTHING` — `fulfillment_shipped:{fulfillment_gid}` / `fulfillment_delivered:{fulfillment_gid}`, keyed on the FULFILLMENT gid (not the order gid) so a split-shipment order gets independent notifications per parcel. **Data sourcing:** template params come from `c.ingest.get_mirrored_order(order_gid)` (the mirror, NOT the fulfillment webhook payload itself — that payload carries no usable order name or customer object) + `customer_display_name(order)` for the name param; a mirror miss skips the notification entirely (gid-only log, still acks 200 — same "degrade, never block the ack" posture as `_mirror_order`/`_mirror_fulfillment`). **Recipient resolution (fixed in the 2026-08-17 security-review round, commit `5aef7aa` — was a real bug in the first-shipped version, commit `1b29f8f`, which used `order.best_phone()` directly):** `to = await c.ingest.get_mapping_phone(order_gid)` FIRST (the original confirmation's actual recipient — already E.164, ranked with `customer.phone` above shipping/billing), falling back to `normalize_phone(order.best_phone())` only if no mapping row exists, and skipping entirely (gid-only log) if neither resolves — `Order.best_phone()` alone omits `customer.phone` and is not guaranteed E.164, so using it directly could silently message the SHIPPING contact instead of the person who actually messaged the bot (a gift/relative order). Mirrors `jobs.reconcile._notify_cancelled`'s identical fix (commit `584b4af`) — see `error_learnings.md` 2026-08-17. **Failure isolation (also the 2026-08-17 fix round):** the shared mirror+mapping-phone read is wrapped in ONE `try/except` (a failure there legitimately blocks both notifications — nothing to send without the order), but the shipped and delivered sends are each independent `_enqueue_and_send_fulfillment_notification` calls with their OWN internal `try/except` — a shipped-send failure can no longer silently drop a same-event delivered send (or vice versa), and each notification's dedupe key is written even if the send itself later fails, so it is not permanently lost. No live courier-tracking integration (a2ship or otherwise) — reacts only to Shopify's own webhook-delivered `shipment_status`, never polls a courier API (Q10 already closed this). No `hi`/`gu` versions — pinned `en` until/unless separately approved in Meta.

## AdminBodyCapMiddleware
- **File:** backend/app/admin/router.py
- **Purpose:** cap `/admin` request bodies at the ASGI layer, before FastAPI parses the body — two rejections so the cap cannot be bypassed at the edge.
- **Public API:** `AdminBodyCapMiddleware(app, max_body=1_048_576)` (pure ASGI); registered via `app.add_middleware(AdminBodyCapMiddleware)`.
- **Used in:** main.app.
- **Notes:** a router-level dependency CANNOT do this — FastAPI parses (and may 422 on) the JSON body before path dependencies run, so an oversized invalid body would 422 before any cap check. Enforced on Content-Length + explicit no-length rejection at the ASGI layer, matching the webhook edges' raw-body posture: (1) `Content-Length` over the cap → **413**; (2) a body-bearing method (POST/PUT/PATCH) with NO `Content-Length` header — e.g. chunked transfer-encoding, which would otherwise skip the header check and reach a pre-auth route unbounded — → **411** (length required). Browsers/fetch always send Content-Length for JSON, so 411 rejects only unusual clients. Only inspects `/admin` paths.

## Cancel reconciliation job — Phase 5
- **File:** backend/app/jobs/reconcile.py
- **Purpose:** apply the FINAL `cancelled` tag once Shopify confirms an order is actually cancelled (`orderCancel` is async), and — **2026-08-16, new capability** — notify the customer with the `cod_cancel` template once that happens (this job sent nothing before this feature).
- **Public API:** `async run_reconcile_cancels(c: Container) -> dict[str, Any]`; registered as the `reconcile_cancels` job. `_RECONCILE_LIMIT = 50`. Module helpers: `async _notify_cancelled(c, cfg, controls, auth, gid) -> Literal["notified","skipped"]` (best-effort `cod_cancel` send — kill-switch gated, "skipped" for every non-send branch: no deliverable phone, suppressed, >=400 Meta response, or transport failure); `async _release_claim(c, gid) -> None` (reverts a claimed order back to `cancel_requested` on any skip/failure so the next run retries it; a store-layer error here is logged and swallowed, never aborts the batch). `_CANCEL_TEMPLATE = "cod_cancel"`, `_CANCEL_TEMPLATE_LANGUAGE = "en"` (Meta-approved in `en` ONLY, same as `cod_confirmmsg`/`cod_confirmation`/`prepaid_order`, Q19c — pinned regardless of the order's detected language).
- **Used in:** jobs.router (JOBS registry → `POST /internal/jobs/reconcile_cancels`, CRON_SECRET-authed).
- **Notes:** **Claim state machine (three states, 2026-08-16 — was a plain status filter with no claim):** a mapping sits at `cancel_requested` until a run atomically CLAIMS it via `ingest.orders_awaiting_cancel_reconcile(50)` into the transient `cancel_reconciling` status (`FOR UPDATE SKIP LOCKED` + a 10-minute stale-reclaim — see the `IngestStore` entry), so two overlapping runs never double-process the same order and `cod_cancel` is never double-sent from that race. Every claimed gid is finalized within the run: advanced to `cancelled` on success, or RELEASED back to `cancel_requested` via `_release_claim` on any skip/failure (missing order, not yet cancelled per Shopify, no phone to authorize, or a `ShopifyError`) so the row is not lost. **Per-gid flow:** re-fetch live via `c.shopify.get_order(gid)`; only when `order.is_cancelled()` (cancelledAt set) → `authorize_own_order(order)` (constructs the `AuthorizedOrder` from the order's own best phone INSIDE `core.order_resolver`, so ADR-004's "only order_resolver builds it" holds) → `add_tags(auth, controls.tags.cancelled)` + `set_mapping_status(gid,"cancelled")` + `record_order_action(gid,"cancelled","system",None,"ok",None)`, THEN (if the WhatsApp config loaded) `_notify_cancelled`. This keeps a false `cancelled` tag from ever being written before Shopify actually cancels (ADR-004 #3). **`_notify_cancelled`'s phone resolution:** prefers `ingest.get_mapping_phone(gid)` (the order's actual conversation phone, already E.164) over `auth.verified_phone` normalized via `core.phone.normalize_phone` — `auth.verified_phone` is a RAW Shopify string (not guaranteed E.164), so sending it straight to Meta risked a bare 10-digit number resolving under the wrong country code and delivering the customer's name + order number to an unrelated person (found + fixed in review, commit `584b4af`); neither resolving → skip (gid-only log, no PII). **Kill-switch gating (new for this job, 2026-08-16):** `send_decision(controls.send_mode, controls.allowlist_phones, to)` is checked before every `cod_cancel` send — `suppress` skips the notification but the tag/status write and `reconciled` count are UNAFFECTED (the kill switch affects notification only, never the mutation). A missing/corrupt WhatsApp config (`load_whatsapp_config` raising `VaultError`) is caught ONCE per run (not per-order) and disables notifications for the whole run without affecting reconciliation. A `>=400` Meta response (`result.ok is False`) and a `WhatsAppSendError` (transport) are both logged (`result.error` already token-redacted) and degrade to `"skipped"` — never rolls back the tag/status write, never aborts the batch (added 2026-08-16, commit `584b4af`, "log send failures" — a failing send was previously silently swallowed with no visibility). Returns `{checked,reconciled,pending,skipped,notified,notify_skipped}` (the last two counters new 2026-08-16). **⚠ Documented, accepted residual risk (not a TODO):** the success path writes the tag BEFORE it advances the status (`add_tags` → `set_mapping_status("cancelled")` → notify) — a crash between a successful `add_tags` and `set_mapping_status` leaves the row stuck at `cancel_reconciling`; the 10-minute stale-reclaim then re-processes it, re-applying `add_tags` (idempotent, harmless) but possibly re-sending `cod_cancel` (a POSSIBLE duplicate customer notification). Bounded in practice: a Vercel invocation times out far short of 10 minutes, so a genuinely still-running process can never collide with its own stale-reclaimed row (both a code review and an independent security review judged it practically closed; reordering the writes is explicitly out of scope). **⚠ Not yet verified against real Postgres:** the atomic-claim concurrency test `backend/tests/store/test_reconcile_claim_pg.py` is gated on `TEST_DATABASE_URL`, which was UNSET in the review environment — the `FOR UPDATE SKIP LOCKED` claim behavior itself has not been proven against a live Postgres instance yet; flagged as a pre-cron-wiring verification step (see `_pipeline_status.md`).

- **Deliberate design deviation from the router's usual error-response pattern:** the two send-outcome failure branches (`WhatsAppSendError` caught, or `SendResult.ok is False`) do NOT `raise HTTPException` (which would produce FastAPI's default `{"detail": ...}` body) — they set `response.status_code = 502` on an injected `fastapi.Response` param and `return {"ok": False, "error": ...}` directly, so every response from this endpoint (success or failure) shares the same `{"ok": bool, ...}` top-level shape the admin UI reads. The 404/400/503 branches (unknown thread, empty text, WhatsApp not configured) still use the router's normal `raise HTTPException`, since those callers don't need the `ok`-keyed body.
- **`wa_cfg is None` guard (503):** not present in the design doc's illustrative code sample — added because `load_whatsapp_config` returns `WhatsAppConfig | None` and `send_text` requires a non-Optional `WhatsAppConfig` (mypy strict `[arg-type]` otherwise); mirrors `core/conversation.py::_run_turn`'s own `if wa_cfg is None: return` early-exit for the same reason.
- **`GET /admin/conversations/{thread_id}` change:** `ai_reply` entries (only) gain `entry["sender"] = msg.sender` alongside the existing `entry["delivery_status"]` — additive, gated on `msg.role == "assistant"` exactly like `delivery_status` already is.
