## [POST /webhooks/shopify]
- **Handler:** backend/app/channels/shopify_webhook.py (`shopify_webhook()`)
- **Request:** raw Shopify webhook body (JSON); headers `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`.
- **Response:** 403 `forbidden` (signature verifies under NEITHER configured secret, or both unset/unreadable); 200 `{"ok": true, "ignored": true}` (unhandled topic, missing webhook id, or unparseable/non-dict body); 200 `{"ok": true, "duplicate": bool, "queued": bool}` on `orders/create` ingest; 200 `{"ok": true, "ignored": bool}` for the mirror-only topics (`orders/updated`, `customers/update`, `fulfillments/create`, `fulfillments/update`).
- **Handled topics (2026-08-14):** `HANDLED_TOPICS` is DERIVED from `subscriptions.REQUIRED_TOPICS` (now `ORDERS_CREATE, ORDERS_UPDATED, CUSTOMERS_UPDATE, FULFILLMENTS_CREATE, FULFILLMENTS_UPDATE`). `fulfillments/create`+`fulfillments/update` parse via `shopify_orders.fulfillment_from_webhook_payload` (the order gid is CONSTRUCTED as `gid://shopify/Order/{order_id}` — the fulfillment payload carries only the numeric `order_id`, not an order gid) and mirror via `_mirror_fulfillment` → `ingest.upsert_fulfillment` (soft-fail, never aborts the ack, same posture as `_mirror_order`). These deliver only after an order is fulfilled and require the `read_fulfillments` scope; if the scope is not granted, `ensure_subscription`'s per-topic isolation reports those two topics as `"error"` while the other three subscribe fine (no code change, degrades cleanly). **Delivery-date limitation (2026-08-15, Q18 groundwork):** the REST fulfillment webhook payload carries NO delivery-date field (only `shipment_status`, a string enum — not a timestamp), so `fulfillment_from_webhook_payload` cannot populate `Fulfillment.delivered_at` (it always leaves it None). The actual delivery timestamp (`deliveredAt`) is available ONLY via the Admin GraphQL read path (`get_order_fulfillments` → mirror write / backfill) — the webhook-push path cannot capture it. See component_registry `Fulfillment` + `upsert_fulfillment` notes. **Fulfillment lifecycle notifications (2026-08-17, was mirror-only — the gap this closes):** after `_mirror_fulfillment` succeeds, `_notify_fulfillment_events(c, order_gid, fulfillment, payload)` runs unconditionally on every `fulfillments/create`/`fulfillments/update` delivery — sends `order_shipped` (pinned `en`, positional `[name, order.name, tracking_company, tracking_url_or_number]`) the first time a fulfillment has both a tracking company AND a tracking number/url, and `order_delivered` (positional `[name, order.name]`) when the SAME raw payload's `shipment_status == "delivered"` (Shopify's own field, read directly off the raw dict, not the parsed `Fulfillment`). Both checks run independently on every event; idempotency is the existing `outbound_messages.dedupe_key UNIQUE` constraint, keyed per fulfillment gid (`fulfillment_shipped:{fulfillment_gid}` / `fulfillment_delivered:{fulfillment_gid}`) so a split-shipment order gets independent notifications and a webhook replay never double-sends. Params come from `c.ingest.get_mirrored_order(order_gid)` (a mirror miss skips the notification, still acks 200, gid-only log). Recipient = `c.ingest.get_mapping_phone(order_gid)` first (the original confirmation's actual recipient), `normalize_phone(order.best_phone())` as fallback only if no mapping exists — see component_registry's new "Fulfillment lifecycle notifications" entry for the recipient-routing bug this fixed (security-review round, commit `5aef7aa`) and `error_learnings.md` 2026-08-17. Each of the two notifications is enqueued+inline-sent independently (own `try/except`, own dedupe key) via the now-generic `jobs.outbox_drain.send_inline_outbound(..., timeout=2.0)` — see that job's registry entry for the widened generic `payload_json` envelope (`{template, language, body_params: dict|list, image_url?, buttons?}`) both this path and the original `cod_confirmation`/`prepaid_order` push now share. No live courier-tracking integration; no `hi`/`gu` template versions (pinned `en`, same as every other template here).
- **Notes:** HMAC = base64(HMAC-SHA256(raw body, secret)), constant-time. **Dual-secret transition (2026-08-14):** the signature is accepted if it verifies under EITHER `shopify:client_secret` (app-created subscriptions via `webhookSubscriptionCreate`) OR, if configured, `shopify:webhook_signing_secret` (the per-store secret from Admin → Settings → Notifications, for webhooks the owner creates manually). `_hmac_verifies(c, key, raw, header)` tries client_secret first (the live real-order path — one `get_secret` call when it matches), falls through to the signing secret only if the first doesn't verify; each check fails CLOSED independently — an unset key (`get_secret` None) or an unreadable/corrupt one (`VaultError`) just doesn't verify and never crashes the request nor blocks the other secret. This is additive: `subscriptions.ensure_subscription` (app-managed) is unchanged. The atomic `IngestStore.ingest_order_created` transaction is followed by the mirror sync (best-effort, non-fatal), then the WhatsApp send, then the ack (ADR-001; a 5xx before the ack → Shopify retries). **INLINE send is now the PRIMARY trigger (ADR-001 amendment, owner-directed 2026-08-15):** the handler `await`s `jobs.outbox_drain.send_inline_outbound(c, result.outbound_id)` — a genuine bounded `await` before the response — because the external scheduler the owner relied on for the cron drain stopped working. This is NOT `BackgroundTasks`/`create_task` (those don't reliably run after the response on Vercel's Python runtime — the reason the 2026-08-13 self-invoke experiment was reverted); the ack is legitimately delayed by the send, so the WhatsApp call is bounded by `_INLINE_SEND_TIMEOUT_SECONDS = 3.0` (distinct from the drain's 20s default) to keep the whole handler under Shopify's <5s ack budget. Safety: the inline path claims ONLY the row just queued (`result.outbound_id` → `claim_outbound_by_id`, atomic `queued→processing`), so the backstop drain can never double-send it; a failure/timeout leaves the row re-claimable and NEVER raises past the boundary (the ack is always 200 `{"ok","duplicate","queued"}`); the `send_mode` kill switch is enforced exactly as elsewhere (`off` leaves it queued, shadow/allowlist-miss suppress with zero Meta calls). **`/internal/jobs/outbox_drain` is retained as a manual/backstop tool**, no longer the primary sender. `dedupe_key UNIQUE` keeps delivery exactly-once per order regardless of how many times any path sees the row. Idempotent on `(webhook_id, topic)`. Eligibility from config `push_policy` (default `cod_only`) + `push_staleness_hours` (default 6, parsed via `_staleness_hours` = ASCII-digit gate + `math.isfinite` + range clamp → 6.0 so a corrupt/Unicode/non-finite stored value can't 500 the signed hot path — security-review 2026-08-06); queued push dedupe_key `order_created:{gid}`. **Q19 (2026-08-15) — new template + richer payload:** the template send language is PINNED to `TEMPLATE_LANGUAGE = "en"` (both templates below are Meta-approved in `en` only, so sending the customer's hi/gu locale would reject; the free-form conversation still uses the customer's language). **2026-08-16 — order-type routing (was `TEMPLATE_NAME = "cod_confirmation"` hardcoded for EVERY order, prepaid or not — a real bug: a prepaid customer got asked to "confirm" a COD order they already paid for, with a Cancel button):** `TEMPLATE_NAME_COD = "cod_confirmation"` for a COD order (`incoming.is_cod()`), `TEMPLATE_NAME_PREPAID = "prepaid_order"` for a prepaid order — same 6-named-field payload shape for both (`prepaid_order` has no BUTTONS component approved on the WABA; `jobs.outbox_drain` attaches Confirm/Cancel buttons only when `payload.template == "cod_confirmation"`, so a prepaid push is informational-only). Prepaid orders get NO automatic Shopify tag and no mapping-status change (the `confirmed` tag stays meaningful specifically as "confirmed via a button tap," which structurally can't happen without buttons). Outbox payload_json: `{template:"cod_confirmation"|"prepaid_order", language:"en", customer_name, order_id, product_name, product_color, product_size, product_amount, [image_url]}` — 6 NAMED body params (first line item only, Q19b) + an OPTIONAL `image_url`. **Image resolution happens HERE at ingest time** (`_resolve_product_image` → `shopify.get_product_image_url(incoming.product_gid)`, bounded by `_IMAGE_FETCH_TIMEOUT_SECONDS = 2.0`, best-effort): the URL is cached in payload_json so the inline send + backstop drain + reminder all reuse it with ZERO extra Shopify work and the sender stays a pure formatter. Q19a: a failed/timed-out fetch degrades to no `image_url` (send with no header), never blocks/crashes the confirmation; a rare ack-budget overrun is a SAFE idempotent Shopify retry (webhook_id dedupe + claim-by-id no-double-send). Missing product/order fields degrade to `"-"` (Meta rejects empty named params).

## [POST /webhook/whatsapp]
- **Handler:** backend/app/channels/whatsapp.py (`receive_webhook()`, dispatches fresh `InboundText` to `app.core.conversation.run_turn()`)
- **Request:** raw Meta webhook body (JSON); header `X-Hub-Signature-256: sha256=<hex>`.
- **Response:** 403 `forbidden` (bad/missing HMAC or unconfigured); 413 if body > 1 MiB; 200 `{"ok": true, "ignored": true}` (foreign `phone_number_id`, status callback, unparseable/non-dict body, or unknown message type); 200 `{"ok": true, "processed": N, "duplicate": N, "results": [{"message_id", "duplicate", "event_type"}, ...]}` for a delivery (batch-aware; one entry per message).
- **Notes:** HMAC = **hex**(HMAC-SHA256(raw body, config `whatsapp:app_secret`)), constant-time (distinct from Shopify base64). Idempotent on Meta `message_id` via `MessageStore.record_if_new`. **Task 14 (Phase 4):** every fresh `InboundText` now runs the router + 5-agent pipeline and (gated) sends the reply, BEFORE the response is built, still inside the request (no queue) — a pipeline failure is swallowed by an internal `except Exception: logger.exception(...)` so the webhook still 200s the already-deduped message; a turn that runs past `TURN_TIMEOUT_SECONDS` (55s, chosen to sit comfortably under whatever the deploy's function timeout ends up being) is caught as `except TimeoutError` and logged as a WARNING instead of an uncaught platform 504 (2026-08-06 security-review fix — see below). Gates (see component_registry.md's `app/core/conversation.py` entry for the full order): `AdminControls.send_mode` `off` = pipeline does not run at all (no Shopify/LLM call); `shadow` = runs + persists but never `send_text`; `allowlist` = sends only to `controls.allowlist_phones`; `live` = always sends. `conversations.paused_until` (human took over) = the message IS still persisted via `append_message` but no router/agent/send runs. **Phase 5 button dispatch (2026-08-10):** a fresh `InboundButton`/`InboundInteractive` now runs `dispatch_button(c, event)` (deterministic confirm/cancel → `tagsAdd`/`orderCancel`, NO LLM) at the same `event_type` seam. The webhook keeps a coarse off-gate (raw `send_mode` config key read once per delivery; only `shadow`/`allowlist`/`live` reach dispatch, `off`/unset/corrupt = disabled), but the AUTHORITATIVE kill switch now lives INSIDE `dispatch_button` (Phase-5 review fix 2026-08-10): it calls `send_decision(send_mode, allowlist_phones, wa_id)` first and, on `suppress` (shadow, allowlist-miss, off, unknown), does nothing at all — no re-fetch, no mutation, no reply — so a shadow-mode or allowlisted-out tap has NO live Shopify/WhatsApp effect (previously it performed REAL mutations + sends in shadow). Single source of truth, mirroring the drain and the inbound conversation path; the webhook gate is defense-in-depth. A tap is processed even for a paused/handed-off conversation (a deterministic tap is not a "conversation"). The dispatch is wrapped so a handler error never 500s the signed webhook (still acks 200). **Delivery/read receipts (2026-08-18, Task 5):** the handler now also calls `extract_statuses(payload, expected_phone_number_id=cfg.phone_number_id)` (same fail-closed tenant guard as `extract_events`) and, for each parsed `InboundStatus`, `await apply_delivery_status(c, wa_cfg, status)` (from `app.core.apply_status` — tries `IngestStore.apply_outbound_delivery_status` first, then `ConversationStore.apply_message_delivery_status`; signature widened 2026-08-18 to also take `wa_cfg` — see the Delivery-Failure Auto-Retry note below). This runs BEFORE the `if not events: return {"ignored": true}` early return, because Meta delivers delivery/read status callbacks in their OWN webhooks with no `messages` array — putting it after the early return would drop every status-only delivery. Each apply is wrapped in `try/except Exception: logger.exception(...)` so a status-processing failure never fails the signed webhook's 200 ack (same discipline as `dispatch_button`). A status-only delivery still returns `{"ok": true, "ignored": true}` (no message events), the status side effect having already been applied. **Delivery-Failure Auto-Retry (2026-08-18, sub-project 1e, additive on the same seam):** when `apply_delivery_status` sees a genuinely NEW `"failed"` transition (not a Meta-redelivered duplicate), it now also triggers an automatic resend (`app.core.delivery_retry.retry_failed_outbound`/`retry_failed_message`, capped at `MAX_RETRIES = 3`) through the SAME `send_decision` kill switch as every other outbound send — no bypass. This makes `wa_cfg` a required param since the resend needs it to send. See component_registry.md's "Delivery-failure auto-retry" entry for the full behavior; no new HTTP endpoint or request/response shape change — same 200 ack either way. Ownership is re-checked live per tap via `resolve_by_gid` before any mutation; a non-owner/unknown gid → generic refusal, no mutation, no leak. Never crashes on attacker-typed JSON. **Post-Task-14 security-review fixes (2026-08-06):** (1) **layering** — the pipeline logic moved out of `channels/whatsapp.py` into `app/core/conversation.py` (`fastapi-layering.md`; `channels/` is webhook edge only). (2) **internal `asyncio.timeout` guard** — without it, a worst-case turn (11 config reads + Fernet decrypts + Shopify fetches + two LLM calls + the WhatsApp send) risked an uncaught platform 504 whose retry would be silently dropped as a duplicate (message already marked seen), losing the reply with nothing logged. **`vercel.json` itself is UNCHANGED** (an earlier attempt to add `functions["api/index.py"].maxDuration` there was reverted the same day — `functions` and `builds` are mutually exclusive in Vercel's schema and this repo's `vercel.json` needs `builds`/`routes` for its catch-all ASGI routing; adding `functions` would have broken the next deploy outright). `maxDuration` must be set via the Vercel dashboard (Project Settings → Functions) once the project is connected — a deploy-time step, tracked in `_pipeline_status.md`, not a code TODO. (3) **failed-send logging** — `SendResult.ok is False` is now checked and logged (`whatsapp send failed: status=%s error=%s`, `error` already secret-redacted) instead of silently discarded. (4) **empty-reply guard** — a reply that strips to blank (e.g. a completion that's only a code fence) falls back to `copy_for("error_fallback", "en")` before persist/send.

## [GET|POST /internal/jobs/{name}]
- **Handler:** backend/app/jobs/router.py (`run_job()`)
- **Request:** path `{name}`; auth by method — **`GET` reads `Authorization: Bearer <CRON_SECRET>`** (Vercel Cron fires GET and auto-injects this header when the env var is named `CRON_SECRET`), **`POST` reads `X-Cron-Secret`** (manual/admin trigger). Each method reads ONLY its own header (a GET with `X-Cron-Secret` but no `Authorization`, or a POST with `Authorization` but no `X-Cron-Secret`, is rejected).
- **Response:** 503 if `settings.cron_secret` unset/<16 chars; 403 on secret mismatch/missing/non-ASCII/wrong-header-for-method; 404 unknown job; 502 `{"job","error":"job failed"}` on a `ShopifyError` (text never echoed); 200 `{"job": name, "result": ...}`.
- **Notes:** constant-time secret compare (F11), shared by both header paths via `_secret_matches` (ASCII-encode-then-`compare_digest`, fail closed on non-ASCII). `_provided_secret(request)` picks the header by `request.method`. Registered jobs: `ensure_subscription` (→ `{"status": "ok|created|updated"}` or `{"error": "public_base_url not configured"}`); `retention_purge` (DPDP age-based purge — reads config `retention_days`; default 0 → `{"status": "disabled"}` no-op; when >0 → `{"status": "purged", "retention_days", "deleted": {...}}`); **`outbox_drain` (Phase 5 — Flow A send drain, ADR-002 kill switch; the BACKSTOP WhatsApp send trigger since the 2026-08-15 inline-send amendment — the `orders/create` webhook now sends inline as the primary path; this endpoint is retained for manual/backstop runs and can still be driven by a Vercel Cron `{"path":"/internal/jobs/outbox_drain","schedule":"* * * * *"}` if one is configured)** → `{"drained":0,...,"reason":"send_mode off"}` when off, `{"drained":0,"error":"whatsapp not configured"}` when unconfigured, else `{"drained","sent","suppressed","failed","undeliverable"}`; **`reconcile_cancels` (Phase 5, 2026-08-10 — apply the final `cancelled` tag once Shopify confirms cancelledAt; 2026-08-16 — also sends the `cod_cancel` template to the customer once that happens, this job's first-ever outbound send, kill-switch gated via `send_decision`)** → `{"checked","reconciled","pending","skipped","notified","notify_skipped"}` (last two counters new 2026-08-16); **`send_reminders` (Q17, 2026-08-14 — resend the `cod_confirmation` template ONCE to orders still at `status='template_sent'` 1 hour after the original push; queues a `order_reminder:{gid}` outbox row that the existing drain then sends; driven by a NEW Vercel Cron in `vercel.json` → `{"path":"/internal/jobs/send_reminders","schedule":"*/5 * * * *"}`)** → `{"swept","queued"}`. All are idempotent + safe to re-run.

## [admin] Auth — POST /admin/login, GET /admin/session
- **Handler:** backend/app/admin/router.py (`login()`, `session()`)
- **Request:** login `{"password": str≤256}`; session none (cookie only).
- **Response:** login 503 if `ADMIN_PASSWORD` unset, 401 on wrong password, 429 over 5/min, 200 `{"ok": true}` + httponly `admin_session` cookie (SameSite=strict, **Secure when `settings.app_env == "prod"`** — server config, NOT the client `x-forwarded-proto`; path=/admin, 12h); session 401 without a valid cookie, 200 `{"ok": true}`.
- **Notes:** password compared constant-time (`check_password`); empty stored password never grants access. Login success/failure/not_configured is audit-logged (actor-free, never the password, 2026-08-06). Cookie is an HMAC-signed expiring token (`app_master_key`), verified by `require_admin`. `GET /admin/session` does NO DB access (a DB hiccup can't log anyone out). Rate limit via slowapi keyed on remote address. All `/admin` requests >1 MiB Content-Length → 413 (`AdminBodyCapMiddleware`, before body parse). **Security-review (2026-07-30):** (a) cookie Secure from `app_env`, prod always forces it; (b) EVERY `/admin` response (JSON API + `/admin/ui`) carries `Content-Security-Policy` / `X-Frame-Options: DENY` / `X-Content-Type-Options: nosniff` / `Referrer-Policy: no-referrer` / `Cache-Control: no-store` (`AdminSecurityHeadersMiddleware`); (c) a body-validation 422 (any route) NO LONGER echoes the submitted `input` — a global `RequestValidationError` handler strips `input`/`url`/`ctx`, so over-length creds (password/api_key/client_secret/access_token) never reach the error body.

## [admin] Credentials — GET|POST /admin/shopify, GET|POST /admin/whatsapp
- **Handler:** backend/app/admin/router.py (`shopify_status`/`set_shopify`, `whatsapp_status`/`set_whatsapp`)
- **Request:** shopify `{"client_id"?, "client_secret"?, "webhook_signing_secret"?}` (≤256 each); whatsapp `{"phone_number_id"?, "waba_id"?, "api_version"?, "access_token"?, "app_secret"?, "verify_token"?}`.
- **Response:** shopify GET `{"configured": bool, "webhook_signing_secret_configured": bool}` (`configured` = client_id+client_secret both set; the signing-secret flag is independent); whatsapp GET `{"configured": bool, "phone_number_id", "waba_id", "api_version"}` (NON-secret fields only); POST 422 if first-time setup is missing a required field, 200 `{"ok": true}`.
- **Notes:** require_admin (401). **Secrets are NEVER echoed** — GETs return status/non-secret only. Partial update: blank/omitted keeps the stored value; first-time setup requires the full set (shopify: client_id+client_secret — `webhook_signing_secret` is additive/independent, never part of the first-time gate, written only when supplied; consumed by the dual-secret `/webhooks/shopify` HMAC check). Secrets Fernet-encrypted at rest under `shopify:{client_id,client_secret,webhook_signing_secret}` / `whatsapp:{access_token,app_secret,verify_token}` (secret) + `whatsapp:{phone_number_id,waba_id,api_version}` (plain). **Format validation (security-review 2026-07-30):** whatsapp `phone_number_id`/`waba_id` digits-only (`^\d{5,20}$`), `api_version` `^v\d+\.\d+$` — a bad value → 422 (input not echoed), so path-like junk can't be interpolated into the Graph API URL.

## [admin] LLM provider — GET /admin/providers, GET /admin/config, POST /admin/provider
- **Handler:** backend/app/admin/router.py (`providers`, `provider_config`, `set_provider`)
- **Request:** provider `{"provider": str≤64, "api_key"?: str≤512}` (api_key omitted for env-auth providers).
- **Response:** providers `[{"key","label","default_model","auth_kind"}]` (`auth_kind` ∈ `api_key`|`env`); config `{"configured": bool, "provider": str|null}` (NEVER the key); provider 400 unknown provider / missing key (api_key providers) / verification failed, 200 `{"ok": true}` (or `{"ok": true, "warning": ...}` when a rate-limited-but-authenticated key is accepted).
- **Notes:** require_admin (401). Verifier built via `deps.build_provider(settings)` (`LiteLLMProvider` with Vertex env creds). **api_key providers (gemini):** verify-key-before-save — the key is checked BEFORE it is Fernet-encrypted to `llm:api_key:{provider}` and `llm:active_provider` (plain) is set; verify never leaks the key; on failure nothing is persisted; kind→message mapping (auth/quota/model/timeout), `UNKNOWN` → generic "Could not verify the key with the provider." (never raw vendor text). **env-auth providers (vertex):** verified via env service-account creds with an empty key + the provider's `request_params`; on success `llm:active_provider` is set with NO key stored (nothing under `llm:api_key:vertex`); on failure a SAFE generic message ("Could not verify the provider credentials. Check the service-account JSON, project, and location.") — the raw error is NEVER surfaced (may embed the service-account JSON). `GET /config` reports `configured=true` for an active env provider (no key) OR an api_key provider with a stored key.

## [admin] DPDP erasure — POST /admin/erasure
- **Handler:** backend/app/admin/router.py (`erase_by_phone`)
- **Request:** `{"phone": str}` — E.164 `^\+[0-9]{7,15}$` (ASCII digits only), ≤32.
- **Response:** 401 without a valid cookie; 422 on a non-E.164 phone incl.
